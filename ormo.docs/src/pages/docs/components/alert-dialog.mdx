## Default

Alert Dialog uses the native <code>&lt;dialog&gt;</code> element as a modal alert dialog. It makes the rest of the page inert, contains keyboard focus, focuses the least destructive action by default, closes with <kbd>Escape</kbd>, and returns focus to its trigger.

Use Alert Dialog only when an important message requires an immediate response, such as confirming an irreversible action. Use a standard Dialog for interactions that do not interrupt the user's workflow.

</DemoBlock>

## Anatomy

Compose the trigger, alert message, and response controls:

<CodeBlock
  lang="astro"
  code={`---
import * as AlertDialog from "@ormo/primitives/alert-dialog";
---

<AlertDialog.Root>
  <AlertDialog.Trigger>Delete project</AlertDialog.Trigger>

  <AlertDialog.Content>
    <AlertDialog.Title>Delete this project?</AlertDialog.Title>
    <AlertDialog.Description>
      This permanently deletes the project and cannot be undone.
    </AlertDialog.Description>

    <AlertDialog.Cancel>Cancel</AlertDialog.Cancel>
    <AlertDialog.Action>Delete project</AlertDialog.Action>

  </AlertDialog.Content>
</AlertDialog.Root>`}
/>

Content always renders <code>&lt;dialog role="alertdialog" aria-modal="true"&gt;</code>. The runtime generates IDs and connects Content to Title and Description through <code>aria-labelledby</code> and <code>aria-describedby</code>. Trigger opens Content with the native <code>showModal()</code> method.

## Examples

### Detached triggers

Add <code>for</code> with a Root <code>id</code> when a Trigger must be rendered somewhere else in the document. The value is an ID without a leading <code>#</code>. Multiple detached and descendant triggers can control the same Root.

Ormo connects every matching Trigger to Content with <code>aria-controls</code>, synchronizes its open state, and restores focus to the specific Trigger that opened the dialog.

<DemoBlock code={alertDialogDetachedTriggerDemoCode}>
  <AlertDialogDetachedTriggerDemo />
</DemoBlock>

### Initial focus

Cancel receives initial focus by default because it is normally the least destructive response. Add native <code>autofocus</code> to another control when the alert only communicates information or another response is clearly safer and more likely.

<DemoBlock code={alertDialogInitialFocusDemoCode}>
  <AlertDialogInitialFocusDemo />
</DemoBlock>

### Preventing an action from closing

Cancel and Action close the dialog after their click event. Call <code>preventDefault()</code> synchronously when an action must remain open, such as while validation fails or an asynchronous operation begins. Close it later through the Root browser API when the operation succeeds.

<CodeBlock
  lang="ts"
  code={`const root = document.querySelector("ormo-alert-dialog");
const action = root?.querySelector("[data-ormo-alert-dialog-action]");

action?.addEventListener("click", async (event) => {
event.preventDefault();

const succeeded = await deleteProject();
if (succeeded) root?.close("delete");
});`}
/>

### Pending actions

Action and Cancel use the Ormo Button primitive internally, so they support its <code>pending</code>, <code>disabled</code>, and <code>focusableWhenDisabled</code> states. Pending is presentational state only. Disable the action explicitly to prevent repeat activation, set <code>aria-busy</code> on Content, and announce the eventual result outside the dialog.

<DemoBlock code={alertDialogPendingDemoCode}>
  <AlertDialogPendingDemo />
</DemoBlock>

### Explicit focus restoration

Set <code>finalFocus</code> on Content to a CSS selector when closing the alert should move focus somewhere other than its trigger. This is particularly useful when the confirmed action removes the trigger. For dynamic targets, assign an element to the Root browser API instead.

<CodeBlock
  lang="astro"
  code={`<AlertDialog.Content finalFocus="#next-project">
  <!-- alert contents -->
</AlertDialog.Content>

<h2 id="next-project" tabindex="-1">Next project</h2>`}
/>

## Events

Listen for <code>ormo:alert-dialog-open-change</code> on Root. It fires after Content opens or closes and bubbles across shadow boundaries. Its detail contains <code>open</code>, <code>reason</code>, and <code>returnValue</code>. Reason is <code>trigger</code>, <code>action</code>, <code>cancel</code>, <code>escape</code>, or <code>programmatic</code>.

There is no Astro <code>open</code> or <code>defaultOpen</code> prop. Open Alert Dialog with Trigger or <code>showModal()</code> after the custom element connects — native modal opening requires JavaScript. Prevent Content's native <code>cancel</code> event when Escape must not dismiss an irreversible confirmation. A native <code>&lt;form method="dialog"&gt;</code> submit closes Content with the <code>programmatic</code> reason.

## Accessibility

Follow the [WAI-ARIA Alert Dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/alertdialog/). Every alert dialog needs a concise accessible name and description. Prefer the visible Title and Description parts; use explicit ARIA relationships only when another visible element provides the same information.

Keep the alert message brief enough to be understood when announced as one description. A standard Dialog is more appropriate for long, structured, or exploratory content.

Alert Dialog uses native modal behaviour, which makes the rest of the document inert and provides a backdrop. Do not remove the visual distinction between the dialog and inert page content. Always include at least one visible response button.

Cancel receives focus by default. For an irreversible action, retain that least-destructive focus unless there is a strong reason to override it. A programmatic initial target such as <code>autofocus tabindex="-1"</code> is kept separate from the Tab sequence, so keyboard navigation wraps only through tabbable controls.

When Content closes, focus returns to its Trigger or to the element focused before a programmatic opening. If that element will be removed during the action, provide <code>finalFocus</code> as a selector or assign the Root's <code>finalFocus</code> DOM property.

Nested alert dialogs are supported: focus remains within the topmost dialog, closing it restores focus to its nested trigger, and the parent stays open. Keep nesting exceptional because multiple interruptions increase cognitive load.

Development builds report a missing Content, accessible name, description, response control, multiple Content elements, or a detached Trigger with an invalid target in the browser console.

## Keyboard behavior

- <kbd>Tab</kbd> moves focus to the next focusable element inside Content and
  wraps from the last element to the first.
- <kbd>Shift</kbd> + <kbd>Tab</kbd> moves focus backwards and wraps from the
  first element to the last.
- <kbd>Escape</kbd> closes Content with the <code>escape</code> reason unless
  the native <code>cancel</code> event is prevented.
- Activating Cancel or Action closes Content after consumer click handlers run.

The native modal dialog supplies focus containment and Escape behaviour. Ormo supplies initial focus selection, state synchronization, response controls, events, and focus restoration.

## Styling

Pass your own <code>class</code> values to each part. Public part state hooks are <code>data-state="open|closed"</code>, <code>data-open</code>, Content's brief <code>data-starting-style</code> / <code>data-ending-style</code> transition attributes, and Button's <code>data-disabled</code> / <code>data-pending</code> on Action and Cancel. Attributes prefixed with <code>data-ormo-*</code> on primitive parts are internal runtime selectors, not styling APIs.

While any Ormo modal is open, the document element exposes <code>data-ormo-scroll-locked</code>. That attribute is shared document-level state for Dialog and Alert Dialog — use it to observe or style around background scroll locking. It remains until the final nested or sibling modal closes.

Style the modal surface through your Content class and the inert-page overlay through that class's <code>::backdrop</code>. Native discrete transitions can keep a closing dialog in the top layer without requiring Ormo to delay its semantic closed state:

<CodeBlock
  lang="css"
  code={`.alert-dialog {
  transition:
    opacity 120ms,
    overlay 120ms allow-discrete,
    display 120ms allow-discrete;
}

.alert-dialog[data-starting-style],
.alert-dialog[data-ending-style] {
  opacity: 0;
}

.alert-dialog::backdrop {
  background: rgb(0 0 0 / 55%);
}

@media (prefers-reduced-motion: reduce) {
  .alert-dialog { transition: none; }
}`}
/>

Ormo applies no component CSS. Consumers are responsible for a visible modal surface and backdrop, accessible contrast and focus indicators, viewport-safe sizing, and reduced motion when transitions are added.

## Runtime

Alert Dialog always loads one Astro-processed, deduplicated runtime because opening a native dialog from a separate Trigger and coordinating its parts requires client behaviour. One document-scoped listener and observer coordinate descendant, detached, and dynamically inserted Triggers regardless of how many Alert Dialogs are rendered. The browser continues to own the modal top layer, outside-page inertness, and Escape interaction. Ormo locks background document scrolling and supplies a visibility-aware Tab sequence because native focus wrapping is not consistent across engines.

Scroll locking is shared with Dialog and remains active until the final nested or sibling modal closes. An authored inline <code>overflow</code> value is restored afterward.

Before an Astro client-router document swap, an open alert dialog closes synchronously and restores focus. This lets Astro's own focus-preservation step begin from a meaningful element rather than from content that is about to be removed.
